## Finding A — QIL institutional posture conflicts with an unqualified M3 reading

### Recovered institutional evidence

A June 2026 Agent Ecology / Role Boundary document explicitly describes the current implementation as a **seed lattice** and identifies:

- TYME as the **future continuity orchestrator**;
- QIL as the **future coherence lattice**;
- Hall as the **future synthesis and navigation interface**.

An August 2026 Office Field Blueprint places `Quantum-intelligence-lattice` in the **Research and simulation** repository family. The same blueprint describes federation through QIL / repository adaptation as only **partially represented** and a **future protocol question**.

### Interpretation

These institutional records do not prove that no QIL component has ever run. They do, however, materially conflict with an unqualified registry claim that QIL is already `M3: Fielded` if M3 means demonstrated real-use operation of the QIL system represented by the registry entry.

### Current lineage posture

- identifiable implementation: present;
- development / simulation evidence: present;
- institutional future-state language: present;
- traceable QIL field event: not recovered;
- QIL-specific M3 audit record: not recovered.

### Candidate adjudication implication

The QIL record remains `M3_EVIDENCE_INCOMPLETE`, with increased evidence that the classification may require reconsideration after rubric approval.

Do not downgrade automatically: first confirm whether historical Replit/private/institutional QIL field events exist and what implementation they used.

## Finding C — A genuine AVOT field event exists, but mapping it to `avot_core` requires care

### Recovered institutional evidence

A Notion GitHub Write Attempts record documents a successful bounded field event on 2026-05-30/31:

- actor / active surface: **AVOT Fabricator**;
- requested action: create branch `restoration/write-probe-001` from `main` in `sovereign-codex/Codex-control-center`;
- explicit human approval was requested and granted;
- result: **Succeeded**;
- commit/base reference preserved: `e6c55ff9cb7ef50c4bedec79fc674c3302493ec9`;
- files edited: 0;
- PRs opened: 0.

The record interprets the result as confirmation that AVOT Fabricator could execute a GitHub branch creation operation under explicit approval.

A separate AVOT Engine architecture page describes an **operational / emerging** model in which AVOT-engine is the runtime repository while AVOT-ARCHIVIST, AVOT-forge, and AVOT-TRACE hold specialized branches. It lists AVOT-Forge among the initial active agents / components and records runtime pulse tracking, promotion/review workflows, and AVOT-specific repositories as core components.

### Interpretation

This is the first recovered institutional record that clearly satisfies several elements of the proposed M3 field-event contract for an AVOT participant:

- real external environment: GitHub;
- observed operation: branch creation;
- bounded function: authorized GitHub mutation;
- dated event;
- preserved target, branch, base/commit, authority posture, and result.

However, the event is attributed to **AVOT Fabricator**, while the RUN-002 registry target is `avot_core`, mapped to the `AVOT-forge` / AVOT-core lineage. The architecture records distinguish AVOT-engine runtime, AVOT-forge, AVOT-ARCHIVIST, and AVOT-TRACE as separate components.

Therefore the field event cannot yet be silently treated as proof that the specific `avot_core` registry object was fielded.

### Current lineage posture

- AVOT ecosystem real-use field event: **recovered**;
- field event provenance: **strong**;
- evidence of bounded function: **strong**;
- direct `avot_core` implementation/version mapping: **unresolved**;
- proof that AVOT Fabricator branch creation exercised code or authority implemented by `AVOT-forge` / `avot_core`: **not yet established**;
- `avot_core`-specific M3 audit record: not recovered.

### Candidate adjudication implication

Keep `avot_core` at `M3_EVIDENCE_INCOMPLETE` for now, but open a focused mapping inquiry:

`AVOT Fabricator field event → runtime/tool implementation → repository/version → avot_core relationship`

If that chain resolves to the registry object under review, the recovered event could satisfy much of the M3 field-event requirement.

If it resolves instead to a separate ChatGPT tool surface, AVOT-engine runtime, or another adapter, it should become evidence for that component rather than retroactively validating `avot_core`.
